# Isolated browser applications

The `web-application` mode hosts an application on its own HTTPS origin with
cookies, redirects and WebSocket forwarding. The existing HTTP API adapter
retains its restricted response behavior. Application origins never serve the
Isolate control UI, SSH routes or bearer-token API.

## Configuration and DNS

```yaml
api:
  enabled: true
gateway:
  enabled: true
  public_web_url: https://gateway.example.com
dashboard:
  public_url: https://access.example.com
web_apps:
  enabled: true
  launch_ttl: 30
  session_ttl_seconds: 3600
  idle_timeout_seconds: 900
  max_sessions: 100
  max_requests_per_session: 16
protocols:
  enabled: true
  targets:
    '10042':
      protocol: http
      mode: web-application
      project: payments-prod
      upstream: https://wiki.internal.example:8443
      ca_file: /etc/isolate/ca/internal.pem
      public_origin: https://wiki.isolate-apps.net
      bearer_token_file: /etc/isolate/credentials/wiki-token
      allowed_methods: [GET, HEAD, OPTIONS, POST, PUT, PATCH, DELETE]
      allowed_paths: ['/*']
      websocket: true
      max_request_bytes: 16777216
      max_response_bytes: 67108864
      max_websocket_message_bytes: 1048576
      timeout_seconds: 120
      allowed_redirect_origins: []
      client_cookie_names: []
```

The inventory IP pins the upstream and an `http` grant selects the resource.
Use a unique ASCII DNS hostname per app, with an HTTPS certificate and DNS route
to the gateway. Apps require a separate DNS suffix from the control UI, gateway
and configured IdP/trusted endpoint origins. Validation conservatively compares
the last two DNS labels, so even distinct `*.co.uk` sites are refused. Dedicated
domains avoid sharing control/IdP parent cookies; do not serve untrusted sibling
applications on the privileged control domain.

The upstream must be an origin without a base path. Configure the application's
external/public URL and trusted proxy settings for its public origin. Forwarded
host/protocol are generated by Isolate. HTML/JavaScript URL literals are not
rewritten. External redirects are denied unless their HTTPS origin appears in
`allowed_redirect_origins`; relative and upstream-origin redirects are rewritten
to the public origin. Validate an application's external authentication flow
before enabling it; cross-origin mutation/preflight requests are denied.

## Launch and lifecycle

The resource details page has **Open application**. A CSRF-protected control
POST creates a short-lived, single-use code and auto-POSTs it to
`https://<app>/_isolate/launch`. Tokens/codes are absent from URLs, redirect
locations and referrers. API clients may call
`POST /api/v1/web-apps/<host-id>/launch` with a bearer token and
`{"confirm": true}`, then submit the returned code in the same control-origin
launch flow. The application receives only an opaque Secure/HttpOnly,
host-only `__Host-IsolateApp` cookie with SameSite=Lax.
The transition page uses `Referrer-Policy: strict-origin`: browsers retain the
control Origin for CSRF validation while omitting its path and POST credentials.

Launch performs the same current identity, policy, approval, lease and audit
checks as other runtime sessions. One approved session owns all HTTP assets and
WebSockets, including more than 16 requests over its lifetime; the configured
limit of 16 is concurrent requests. Revoked grants, identity logout, control
browser logout, administrator termination, ownership loss, expiry, idle timeout
and recovery epoch changes end it. The configured TTL is capped by the identity
and approval deadlines. A same-origin POST to `/_isolate/logout` ends the app
session explicitly.

The gateway retains live contexts on the owner node. Configure **sticky routing**
for every application host in a multi-replica deployment. Owner restart or routing
to another node requires a fresh launch; approved sessions are never reconstructed
from an old store record. Application state is private control-store data and
follows the existing Redis/SQL backend selection.

## Cookie and upstream boundary

Caller bearer, proxy cookie, forwarded identity and impersonation headers never
reach the upstream. Only the operator's protected upstream token is injected.
Upstream cookie Domain attributes are stripped, Secure is required, and the
reserved proxy cookie cannot be overwritten. A new launch forwards only cookie
values issued during that session; stale cookies from a previous user's session
are filtered. Applications that create cookies in JavaScript must explicitly
allow their names in `client_cookie_names`, typically for non-auth preferences
or CSRF cookies. Do not allow authentication cookie names this way.

Requests and responses preserve compressed bytes and encoding, and are streamed
within configured size/time bounds. WebSockets preserve text, binary messages
and negotiated subprotocols with per-message bounds. Audit records method, path,
status and sizes, excluding query values, cookies, headers and bodies. Application
responses run on the isolated app origin; they are not sandboxed as API HTML.

## Helm

Alongside matching runtime configuration and enabled gateway/API, set:

```yaml
webApplications:
  enabled: true
  className: nginx
  hosts:
    - host: wiki.isolate-apps.net
      tlsSecret: wiki-app-tls
```

The chart renders a full-root TLS Ingress per exact host to the HTTPS gateway.
Default NGINX annotations select HTTPS upstream and cookie affinity. Configure
the actual ingress controller's upstream CA verification, backend SNI and
WebSocket timeouts. Other controllers need equivalent annotations. Do not expose
a plaintext gateway behind a remote TLS terminator: only a local loopback proxy
is accepted for unencrypted development ingress. App certificates belong to the
ingress when it terminates public TLS; configure its backend certificate/SNI
verification independently.
